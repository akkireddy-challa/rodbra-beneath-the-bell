# Generating game assets

The `bitmagic` CLI generates content directly into this project. Eleven types work today:

| Command | Makes | Lands in |
|---|---|---|
| `bitmagic generate skybox --description "..."` | a 360° environment | `worldProfileData.skyboxUrl` |
| `bitmagic generate background --description "..."` | a flat 2D backdrop | `worldProfileData.skyboxUrl` |
| `bitmagic generate block-type --name <id> --description "..."` | a custom voxel block | `worldProfileData.customBlockTypes[]` |
| `bitmagic generate sound --prompt "..."` | a sound effect — for a jump blip or UI tick, Web Audio in code is free and better | `assets[]` |
| `bitmagic generate music --prompt "..." [--duration 30]` | a music track (loops by default; billed per second) — say the assumption line first (below); a 30 s loop is decided, not discussed | `assets[]` (or a file with `--out <mp3> --no-world`) |
| `bitmagic generate image --name <id> --prompt "..."` | a 2D image | `assets[]` |
| `bitmagic character generate --name <id> --prompt "..."` | a rigged character; substitutes a close-enough ready-made one when the library has it (`--fresh` always forges). Add `--reference-image <file>` when the creator hands you a picture it should look like — that redraws the body from their picture and skips the library. `character search --prompt "..."` then `character add --name <id> --id <sid>` instead is **free** and never forges — prefer it when any plausible body will do | `assets[]` |
| `bitmagic generate animation --family gait ...` or `--spec <file>` | an animation clip | `assets[]` |
| `bitmagic generate video --prompt "..." [--duration 5] [--image <png>]` | a short 720p clip for a cutscene (billed per second) | `assets[]`, played with `engine.playVideo("<id>")` |
| `bitmagic generate model --prompt "..."` | a new 3D model | `assets[]` |
| `bitmagic generate vehicle --preset <NAME>` (free; `--preset ?` lists the names) or `--prompt "..."` for a bespoke look | a drivable vehicle | `assets[]` |

`--help` on any subcommand lists its full flags. Which of these — or a forge, a Blender build, a
built-in, or a file of the creator's own — fits a given need, with rough sparks and minutes:
`.agents/skills/choosing-asset-pipelines/SKILL.md`.

## Before a paid generation: say the assumption, ask only when it is expensive

State one line, then run: `Assuming prototype: using <route> (~N sparks, ~T); say polished and I
will use <alt>.` Ask first — recommended option first, answerable in a word — ONLY when the route
is tens of sparks or many minutes (a forge, a long music track, a low-poly character, a bespoke
vehicle) AND the creator has said neither prototype nor polished. Never ask about a free or
seconds-long option; a 30-second music loop or a 3-spark model is decided, not discussed.

**Every `bitmagic` command takes `--original-prompt "<the creator's request, verbatim>"` —
always pass it**, on the everyday loop (`build`, `verify`, `dev`, `reload`, `publish`) as much as
on the generators. It never reaches a generator, so it cannot change the output; it is what the
published page counts as "Built with N prompts", and a game built mostly by editing code runs no
generator at all. Skip it only when no creator request is behind the call.

`animation` is the one that takes no prompt at all: the clip is built from an authored parameter
spec in one of three families — `gait` (the only one with a flag form), `melee` and `oneShot`
(lists of key poses, so they come from a `--spec` file). It is also the cheapest, one spark a
clip, because it is solved locally rather than generated by a model.

`model` is the one to reach for when the game needs an object that does not exist yet — a new
asset from a sentence. It needs Chrome and a free port between 3000 and 3199, because only the
engine can voxelize (a low-poly project keeps the mesh instead — no browser). `--height` scales
it (interiors fill solid below 6 m and stay hollow above, so a building is not baked as a solid
block), and `--name` sets what game code places by. Do not confuse it with `prop`, which
REPLACES an existing placeholder and changes every instance already placed.

`video` makes a short clip for a cutscene. It is the one asset the game does not draw: the row it
writes is played as a fullscreen overlay by `engine.playVideo("<asset id>")`, which resolves when
the clip ends or the player skips it — so it belongs at a story beat, not in the world. Give it
`--name` and that name is what the code calls. A prompt alone generates in well under a minute;
`--image <png>` animates a still you already have (a cover, a reference) but takes a few minutes,
and the clip comes back in the image's shape rather than 16:9. The command leaves 8 frames of it
tiled in `.bitmagic/videos/<asset id>.png` — READ that image before wiring the clip up, and read
the line saying whether it has an audio track, because a silent cutscene needs a music bed under
it. Call `playVideo` from the Play click or later, never before: without a prior user gesture the
browser blocks autoplay and the clip silently does not run. See `video-cutscenes.md`.

`vehicle` is the one that needs more than a prompt to be useful. It creates a NEW asset (it does
not upgrade an existing one), it needs Chrome and a free port between 3000 and 3199 because only
the engine can voxelize, `--preset ?` lists the free presets, and `--preset VAN` builds a standard
vehicle without calling the designer at all — faster, and the right choice when the request does not need a bespoke look. Once it lands,
spawn it by name:

```js
engine.getVehicleSpawner().spawnAndEnterFromAsset({ x: 0, z: 0 }, '<assetName>', playerController);
```

Headlights, taillights and beacons are built and lit automatically — never ask for them.

`background` and `skybox` write the **same field**. Pick one: `skybox` for a 360° panorama a
free-look camera can turn in, `background` for a flat layered backdrop behind a fixed sidescroller
or top-down camera. The engine wraps either onto the sky sphere, so a flat backdrop reads as a
distant painted horizon rather than a full-screen image — and running one after the other replaces
the first, silently.

`block-type` registers a block **before** anything can use it: `--name` is what
`create-voxel-asset`, `groundConfig.surfaceBlockType` and building code refer to, and an
unrecognised name falls back to flat vertex colour instead of failing. Names are lowercase
snake_case, are compared case-insensitively, and cannot shadow a built-in (`wood`, `leaves`,
`stone`, `grass`, `sand`, `dirt`, `ice`, `asphalt`, `water`, `lava`, `marble`, or the
aliases `trunk`, `foliage`, `rock`, `road`). Re-running with the same `--name` **replaces**
the entry rather than adding a second one. `--side-description` gives the side faces their own
texture and generates a second one.

Cover art and the reference image are the two generations that are **not** `generate` subcommands:

| Command | Makes | Lands in |
|---|---|---|
| `bitmagic cover` | the game's cover art | `hud.startScreen.imageUrl`, `.bitmagic/cover.webp`, the publish thumbnail |
| `bitmagic reference make` | a concept image of the world | `.bitmagic/reference/` only — nothing in `world.json` |

`cover` writes its own prompt from `GAME-DESIGN.md` rather than taking one, and re-running it on
an unchanged design generates nothing — it just reports the cover you already have. Rewrite the
design and run it again, or pass `--force`, when the game has moved on from its artwork. It
writes `world.json`, so it invalidates a passing verify: run it before `bitmagic verify`, never
between verifying and publishing. See AGENTS.md for why it is worth running before you start
implementing rather than after.

## The project reference image

`bitmagic reference` manages a concept image of the game's world (see AGENTS.md for when to
offer one). Its subcommands are `make`, `accept <id|url>`, `show` and `clear`; candidates
live in `.bitmagic/reference/` and the accepted choice in `.bitmagic/reference.json` —
nothing in `world.json`, and only `make` costs sparks (the same price as an image).

Once one is **accepted**, `generate skybox`, `generate background`, `generate block-type`,
`generate image`, `bitmagic cover` and `bitmagic forge` all use it as their style reference
by default — the command logs "Using the project's reference image" when that happens. Control it
per call:

- `--no-reference` — this asset should NOT look like the world (a hell-dimension portal in a
  tropical game).
- `--reference-image <file>` / `--reference-image-url <url>` — a DIFFERENT reference for this
  call only; both override the accepted image.
- `bitmagic reference show` — check what is accepted; `clear` stops using it entirely.

**When the human hands you a picture** — "create a world like this", "a skybox like this photo" —
that image IS the reference for that request: save it to a file and pass
`--reference-image <path>` (or `--reference-image-url` if they gave a URL) on the command it
applies to. The CLI uploads the file to the game's storage and forwards its URL; the accepted
project reference is not consulted. Only when they mean it as the game's overall look — "make the
whole game look like this" — run `bitmagic reference accept <file>` instead, which makes it the
project reference everything inherits.

`make` itself never inherits the accepted image — each candidate starts fresh unless you pass
`--from <id>` (or `--reference-image <file>` to iterate from the human's own picture), which is
how "same island, but at dusk" iterations work.

## Before generating

Generating is included in the creator's Bitmagic Pro subscription and the results are good, so the
default answer is yes — a placeholder you left in place to be careful is not the safe option, it is
just a worse game. Two things to settle first:

- **Is there already an asset for this?** If `world.json` holds one that fits, reuse it. That is
  about not doing the same work twice, not about being frugal.
- **Decide the exact prompt.** These are one-shot — you get what you asked for, so there is no
  "generate three and pick one". Spend the thought before the command, not after.

## After generating

1. The command prints which `world.json` paths changed. **Re-read `src/work/world.json`** if you
   are holding it in memory.
2. Run `bitmagic check`, then `bitmagic verify` if the asset is load-bearing — a bad asset URL
   typechecks fine and fails at runtime.
3. A running `bitmagic dev` reloads the browser by itself once the write settles.

## When it refuses

- **Not logged in** — run `bitmagic login`.
- **Does not own the game** — `bitmagic.json`'s `gameId` points at someone else's game; nothing
  was generated and `world.json` is untouched.
- **Insufficient balance** — the message names what was required. That is the Pro allowance plus
  any purchased sparks; `bitmagic usage` shows which is short and when the allowance resets.
- **Allowance used up, spark balance not approved** — the creator has sparks but has not allowed
  them to fund work once the Pro allowance runs out. Report this and stop; only they can run
  `bitmagic allowance --allow-sparks`, and it refuses to run outside a real terminal.

Every failure before the asset arrives leaves `world.json` unchanged, and the command says so
explicitly. You never need to guess whether a failed generation half-applied.

## Adding a file the creator already has

Not a generation, but the same registry: `bitmagic assets add <file>` uploads a `.glb`
(voxelized in a headless browser — Chrome and a free port in 3000–3199, like `vehicle`), a
`.vxl`, an image (`.png/.jpg/.webp`), audio (`.opus/.ogg/.m4a/.mp3`) or a config `.json`
into `assets[]` and prints the id. `--keep-glb` registers a `.glb` as a polygon mesh instead (a
low-poly project's default); `--voxel-size`, `--height`, `--hollow` tune the bake. No sparks. `bitmagic
assets list` shows what is there; `bitmagic assets remove <id>` takes one out of `world.json`
(the file stays in storage) and refuses while something in `world.json` still references it.

## What is not available

Gaussian splats, video, and the import formats `assets add` refuses (`.gltf`, `.vox`, `.qb`,
`.fbx`, `.spz`, `.ply`, `.sog`, `.mp4`) still need the web editor's Assets tab. Do not
hand-edit `world.json` to reference an asset you have neither generated nor added; the game will
fail to load it.
