# Animation Assets — Playing Character Animations

Use when you want a character (player or NPC) to play a one-shot motion: a flip, a punch, a kick, a wave, a kick-the-ball motion, etc.

Animations come from two places:
1. **Built-in animations** — registered in `engine/AnimationAssets.ts`. The active library's required locomotion, idle, jump and flip clips load at startup; optional actions load on demand. Listed below.
2. **Custom animations** — uploaded by the user via the asset pipeline and registered in `world.json` `assets[]` with `type: "animation"`. Loaded on demand via `loadCustomAnimation(motionId)`.

This doc covers playing both kinds via the same API.

## Available built-in animations

Call `playCustomAnimation(motionId, options?)` on the player's animation controller. For an optional or inactive-library clip, first await `loadCustomAnimation(motionId)` when the first trigger must play immediately. Otherwise an unloaded built-in starts a lazy load and returns `success: false`; trigger it again after loading.

| motionId | Name | Duration | Description |
|---|---|---|---|
| `mIdleDefault01` | Idle | loop | Default standing idle (already auto-cycled by state machine) |
| `mWalkDefault01` | Walk | loop | Walk cycle, ~1.8 m/s native speed (auto-played for locomotion below the walk/run threshold) |
| `mQdKavT8ahiz` | SlowRun | loop | Run cycle, ~3.5 m/s native speed (auto-played for locomotion) |
| `m9YxTKJfRZWu` | FastRun | loop | Run cycle, ~5.0 m/s native (auto-played for locomotion) |

## Two built-in libraries — which ids to use

The engine ships two built-in sets, selected by `activeLibrary` in
`engine/AnimationAssets.ts`. **`generated` is currently active**: a hand-authored
library built from source in this repo (see `game/docs/authoring-animations.md`),
replacing the imported Mixamo clips the table above describes.

Both sets stay resolvable — `getBuiltinAnimationDef` searches both — so the ids
above keep working and **nothing you have already shipped breaks**. But new code
should prefer the active library's ids, which are the same clips with an `mGen`
prefix and their own timings:

| Use this | Instead of | Duration |
|---|---|---|
| `mGenIdle01` | `mIdleDefault01` | 4.00s loop |
| `mGenWalk01` | `mWalkDefault01` | 1.00s loop, 1.8 m/s |
| `mGenSlowRun01` | `mQdKavT8ahiz` | 0.70s loop, 3.5 m/s |
| `mGenFastRun01` | `m9YxTKJfRZWu` | 0.58s loop, 5.0 m/s |
| `mGenJump01` | `muwpHn8cHXFR` | 0.90s |
| `mGenForwardFlip01` | `mForwardFlip01` | 1.10s |
| `mGenKicking01` | `mKicking01` | 0.85s |
| `mGenPunching01` | `mPunching01` | 0.75s |
| `mGenSoccerKick01` | `mSoccerKick01` | 0.95s |
| `mGenMiningChop01` | `mMiningChop01` | 0.90s |
| `mGenDance01` | `mDanceUthana01` | 2.00s loop |

Note the one-shots are **substantially shorter** than the clips they replace
(punch 0.75s vs 1.00s, chop 0.90s vs 2.27s). Any code that hardcoded a timeout,
a `setTimeout`, or an `impactTime` against the old durations needs rechecking.

Systems that load clips on demand (`UnarmedMeleeSystem`, `PlayerToolSystem`)
resolve them by clip NAME, so they pick up whichever library is active with no
change on your side.

## Weapon melee moves

`WeaponMeleeSystem` loads a pack of weapon strikes on demand the first time a
weapon is equipped. Eleven moves ship; pick one with `WEAPON_MOVES` rather than
hardcoding an id.

The two-handed set runs PARALLEL to the one-handed set, move for move, so a
greatsword has the same variety as a sword: `heavyChop` ↔ `slashDown`,
`cleave` ↔ `slashSide`, `heavyUp` ↔ `slashUp`, `spearThrust` ↔ `thrust`.
`backCleave` is two-handed-only — it is `cleave` reversed, so consecutive swings
alternate direction instead of the weapon snapping back to the same shoulder:

| `WEAPON_MOVES` key | Move | Best for |
|---|---|---|
| `slashDown` | one-handed overhead chop | sword, katana, cleaver, mace, club, lightsaber |
| `slashSide` | one-handed horizontal swipe | same |
| `slashUp` | one-handed rising diagonal | same |
| `thrust` | one-handed straight stab | sword, dagger, katana, lightsaber |
| `heavyChop` | two-handed overhead smash | longsword, axe, hammer |
| `cleave` | two-handed wide sweep | longsword, axe, staff |
| `spearThrust` | two-handed lunging thrust | spear, staff, polearm |
| `heavyUp` | two-handed rising cut, driven by the legs | longsword |
| `backCleave` | two-handed backhand sweep (cleave reversed) | longsword, axe, hammer, spear, staff |
| `whirlwind` | 360° spin attack | any — the "special" move |
| `guard` | loopable weapon-ready stance | any |


## Unarmed strikes (fighting games)

Eight strikes plus the `FightingIdle` guard stance ship in the generated library — ids in `UNARMED_MOVES`
(AnimationPacks.ts): `cross`, `jab`, `hook`, `uppercut`, `frontKick`,
`roundhouse`, `sideKick`, `sweep`. `UnarmedMeleeSystem` auto-registers
cross + frontKick; load `UNARMED_COMBAT_ANIMATIONS` and register the rest as
custom attacks for a fighting game. Details: `@docs combat-system.md`.

## Ranged weapon animations (aim / fire / grenade)

The `ranged` pack ships six hold styles + grenade throw; weapons resolve to a
hold via `rangedMovesFor(weaponTypeId)` (AnimationPacks.ts) — never hardcode ids:

| hold | aim / fire ids | covers |
|---|---|---|
| pistol | `mGenAimPistol01` / `mGenFirePistol01` | pistol, revolver, laser pistol |
| dual | `mGenAimDualPistols01` / `mGenFireDualPistols01` | dual_* |
| rifle | `mGenAimRifle01` / `mGenFireRifle01` | assault rifle, SMG, machine gun, crossbow, laser blaster |
| shoulder | `mGenAimShoulder01` / `mGenFireShoulder01` | bazooka, grenade launcher, RPG |
| minigun | `mGenAimMinigun01` / `mGenFireMinigun01` (fire LOOPS) | minigun, gatling |
| bow | `mGenAimBow01` / `mGenFireBow01` | bow |

`ThrowGrenade` (`mGenThrowGrenade01`, 0.9s): release the grenade at IMPACT
phase 0.45 — spawn the projectile there, not at clip end. Fire clips play
automatically on shot; `Aim*` loops are opt-in
(`playCustomAnimation(moves.aim, { loop: true })` while aiming down sights).

```typescript
import { WEAPON_MOVES } from 'engine/AnimationPacks.js';

playerController.animationController?.registerCustomAttack({
    name: 'whirlwind',
    animationMotionId: WEAPON_MOVES.whirlwind,
    type: 'attack',
    damage: 18,
    range: 3.0,
    speed: 1.2,
});
```

**Equipping a weapon auto-registers the right move set** — `WeaponMeleeSystem`
picks by weapon type (table in `WeaponMeleeSystem.ts`): a sword swings
slashes + thrust, a hammer/axe/longsword gets the two-handed heavy chop and
cleave, a spear/staff leads with the polearm thrust. A basic attack always plays
the set's horizontal swipe (`primaryMoveFor` in `MeleeWeaponMoves.ts`); the other
moves stay reachable by name through `WEAPON_MOVES`. Custom
weapons registered via `WeaponRegistry.register()` choose by their preset's
`grip: 'one' | 'two'` (absent = one-handed). You only need
`registerCustomAttack` for a *specific* move, a combo, or a special —
`whirlwind` is deliberately never in a default set.

**Soccer / ball kick ⇒ use the `BallSportsSystem` engine system, not a hand-wired clip.** For kicking a ball (soccer, football, penalty, free kick) attach `BallSportsSystem` (`engine/BallSportsSystem.js`) — it plays the built-in `mSoccerKick01` clip on the contact frame and only kicks when the foot reaches the ball. Don't wire `playCustomAnimation('mSoccerKick01', …)` + a manual impulse yourself, and never use the combat clips `mKicking01` / `mPunching01`. Full split in `@docs mechanic-soccer.md`.

**Unarmed combat shortcut:** for any unarmed/punch/kick/fistfight/brawler request, just attach `UnarmedMeleeSystem` (`playerController.setAttackSystem(new UnarmedMeleeSystem(engine, physicsWorld))`). The system auto-registers the two core clips above as `punch`/`kick` `CustomAttackMove`s on character ready — **no manual `registerCustomAttack` calls and no animation-pack load needed**. Full snippet + opt-out + tuning options in `@docs combat-system.md` → "Player Unarmed Combat". Only load the heavier `UNARMED_COMBAT_ANIMATIONS` pack if the design explicitly needs hooks, uppercuts, roundhouses, or a combat-stance idle.

**Auto-played animations** (locomotion + idle + jump + 2nd-jump flip) are wired by the engine's state machine and `PlayerController`. You don't need to trigger them — only override or supplement them with the manually-played ones above.

**Aim-locked running:** `DIRECTIONAL_LOCOMOTION_ANIMATIONS` includes eight-direction
neutral jog and rifle run captures. `RangedWeaponSystem` loads/selects them
automatically; facing-local velocity blends adjacent directions at a shared gait
phase. Walking keeps its existing walk clip. Without the pack, existing
locomotion still works. Template-owned controllers can select a stance through
`setDirectionalLocomotionStyle('neutral' | 'rifle')` and opt out through
`setDirectionalLocomotionEnabled(false)`. Both are optional controller methods.

**Procedural adjustments over clips:** create a named layer with
`setProceduralPoseLayer(name, spec)` (local quaternion deltas, weight, fade-in/out,
duration). For per-frame aiming targets use `updateProceduralPoseLayer(name,
rotations)`; it keeps the envelope running and returns false for missing/releasing
layers. Calling the original setter again intentionally retriggers. Remove with
`removeProceduralPoseLayer(name)`. Joint deltas are bounded; explicit grip/foot
bindings still run afterward. These layers never translate or tilt the physics root.

## Postures (crouch / prone / sit / kneel / swim / climb)

Postures are ENGINE-owned, one call:

```typescript
playerController.setPosture('crouch');   // 'stand' | 'crouch' | 'prone' | 'sit' | 'kneel' | 'climb'
playerController.setPosture('stand');    // returns false if there is no headroom to stand
```

One call swaps all three things a posture is: the animation set (a hold that
replaces idle, and for crouch/prone/climb a move loop that replaces walk AND
run — the crouch step covers every direction), the physics capsule (crouch
0.62x standing height, prone 0.36x — a crouched player fits under a low
ceiling; that is what makes it a mechanic, not a costume), and the move speed
(crouch 0.45x, prone 0.22x, sit/kneel 0 — a seated character does not walk).
Feet stay planted through the capsule change; standing up under a ceiling is
refused (`setPosture('stand')` returns `false`) so the capsule never embeds.
The clip pack loads on first use; until it arrives the standing clips play.

`'swim'` is automatic — attaching a `SwimmingMovement` enters it (tread water
idle, front-crawl stroke) and detaching stands back up. Do NOT wire swim
animations by hand.

Postures (`POSTURE_MOVES` in `engine/AnimationPacks.js`), each a hold and —
where it moves — a move loop: `crouch` (CrouchHold + CrouchStep 0.9 m/s),
`prone` (ProneHold + Crawl 0.6), `sit`, `kneel`, `swim` (SwimTread +
SwimStroke), `climb` (ClimbHold + ClimbUp 0.5 vertical), `supine` (on the
back), `sleep` (arms crossed), `floorSit` (cross-legged), `lean` (shoulder to
a wall on the character's LEFT — turn the character so the wall is there),
`cover` (crouched behind low cover; see below), `ledgeHang`, `push` (PushStep
0.7, shoving a heavy object), `carry` (CarryHold + CarryStep 1.4, a box on the
chest), `ride` (astride a mount/saddle; the mount owns position).

Posture ACTIONS on the player controller, all engine-owned:

- **Cover** — `setPosture('cover')`, then `setCoverPeek(true|false)` rises
  over the top / drops back. With a `RangedWeaponSystem` attached the peek is
  AUTOMATIC from the aim state (aim/fire = up, release = down); games without
  guns drive it from a key.
- **Ledge** — `tryGrabLedge()` probes for a wall ahead with a standable top
  0.9–2.3 m above the feet (and headroom on top) and hangs from it;
  `mantle()` pulls up and over, committing the clip's rise so the character
  ends standing ON the ledge (crouched if there is no headroom). Both return
  false when nothing grabbable is ahead — bind them to a jump-near-wall or a
  dedicated key.
- **Vault** — `vault()` clears a waist-high THIN obstacle (top ≤1.2 m, floor
  within 1.4 m past it) in one motion; returns false otherwise (a thick one is
  a ledge — mantle it).
- **GetUp** — `getUp()` from `supine`/`sleep` to standing (knockdown
  recovery, revive). **Slide** — `slide()` knee-slide one-shot while moving.

Nothing above runs per frame unless an action is in flight.

Wire a crouch KEY only when the prompt calls for it (stealth, cover shooters,
tunnels) — it is opt-in per game, not a default control. A custom-styled
crouch gait (a zombie crouch, a heavy armored crouch) can be AUTHORED with a
`gait` spec using the `hipCap` dial (~66 sneak, ~55 deep) and a low
`designSpeed` (0.7-1.1) — but while a posture is active the engine's own
posture clips take precedence over `setAnimationOverride`, so a custom crouch
gait is a standalone locomotion style (install it on WALK/RUN while
STANDING, e.g. a permanently hunched character), not a replacement for the
built-in crouch step.

## Triggering an animation

```typescript
// In template code (game/src/work/), with a reference to the player controller:
playerController.animationController?.playCustomAnimation('mPunching01', {
    fadeInDuration: 0.15,        // crossfade-in from current pose (default 0.3s)
    fadeOutDuration: 0.2,        // crossfade-out to next state (default 0.3s)
    speed: 1.5,                  // playback rate (1 = normal, 2 = double speed)
    filterRootMotion: true,      // lock hips position track — rotates in place
    splitBodyOnRun: true,        // upper body only while running; legs keep cycle
    interruptOnMovement: true,   // movement input aborts the clip mid-swing
    onFinished: () => { /* optional callback */ },
    onImpact: () => { /* fires once on the auto-detected contact frame */ },
    impactTime: 0.3,             // clip-local seconds; overrides auto-detection
});
```

The animation plays on **track B** (a separate Mixamo player layered over locomotion). Track A keeps updating underneath, even during a full-body action. When `splitBodyOnRun` is off, the full body blends into the action; when it is on AND the player is walking or running, the upper body plays the action while the legs keep cycling. When the clip ends it crossfades back to the current locomotion state, not a frozen pre-action state.

**Use `splitBodyOnRun: true` for any upper-body action** — punches, throws, casting gestures, waves, salutes. Without it the legs snap to the clip's leg pose and look wrong while the player is running.

### Common patterns

**Punch on a button press** (mirrors a melee strike during a run — legs keep going). Snappy 1.5× playback — punches feel sluggish at 1.0×:
```typescript
window.addEventListener('keydown', (e) => {
    if (e.code === 'KeyF') {
        playerController.animationController?.playCustomAnimation('mPunching01', {
            speed: 1.5,
            fadeInDuration: 0.1,
            fadeOutDuration: 0.15,
            filterRootMotion: true,
            splitBodyOnRun: true,
        });
    }
});
```

**A custom action with a physical effect** — keep the clip's root motion if the motion IS the action, play at 1.5× for snappy contact, and `interruptOnMovement: true` so movement input aborts it mid-swing:
```typescript
playerController.animationController?.playCustomAnimation('mThrow01', {
    speed: 1.5,
    filterRootMotion: false,    // keep the step-forward translation
    interruptOnMovement: true,  // movement input cancels the action
    onImpact: () => { /* spawn the projectile here — fires on the contact frame */ },
});
```
(For a **soccer kick**, don't wire this by hand — use the `BallSportsSystem` engine system, which does the clip + contact-frame impulse + foot-contact gating for you. See `@docs mechanic-soccer.md`.)

**Apply physical effects in `onImpact`, never before the clip starts.** Any
action animation that produces a physical effect — a kick's ball impulse, a
punch's hit, a throw's projectile spawn — MUST apply it inside the
`onImpact` callback. The engine auto-detects each action clip's contact frame at
load (works for built-in, user-uploaded, and AI-generated clips alike), so
`onImpact` fires at the moment of contact with no manual timing. Pass
`impactTime` (clip-local seconds) only to override a wrong or absent detection.
Firing the effect up front makes the ball/projectile leave before the limb has
moved — the most common "feels wrong" bug in these mechanics.

**For NPCs**: the same `playCustomAnimation` is on the NPC's animation controller. Trigger from behavior code (e.g. attack range check) instead of input events.

## Bundling — only what's used ships

For published / standalone builds, animations are bundled-on-demand. The bundler scans the compiled game code in `work/` for each animation's motionId or filename; an animation only ships if it's referenced. The exceptions, which are always bundled for a game with a humanoid because the engine state machine relies on them, are the ACTIVE library's idle, walk, slow/fast run, jump and forward flip (`ENGINE_REQUIRED_MOTION_IDS` in `game/scripts/generate-asset-manifest.mjs`) — under the current `generated` library that is the `mGen*` set, not `mIdleDefault01` and friends; an inactive-library id ships only if the game's code names it.

What this means in practice:
- **Just write `playCustomAnimation('mPunching01', ...)` in your game code.** No registration step. The bundler picks it up automatically because the motionId string appears in the compiled JS.
- **Don't add a built-in animation to `world.json` `assets[]`** to "make sure it ships". That array is for *user-uploaded* animations only — adding a built-in there has no effect on bundling.
- **Combat packs ship as a unit.** If you call `loadAnimationPack(MELEE_WEAPON_ANIMATIONS, …)`, all clips in that pack bundle. If you don't, none do.

## Custom animations (uploaded + agent-generated)

Two paths add an entry to `world.json` `assets[]` with `type: "animation"`:

- **User upload** via the creator UI's asset pipeline → `source: 'uploaded'`.
- **Agent generation** via `generate-animation` tool (authors the clip from a parameter spec against the canonical Mixamo skeleton — there is no text-to-motion backend and no fallback: an unexpressible spec is refused with the failing field named) → `source: 'generated'`. Gait clips also record `designSpeed` so locomotion playback speed-matches actual movement. `bitmagic generate animation` runs the same builder server-side via `POST /api/cli/v1/assets/animation/stream`; both lanes charge the same one spark a clip.

- **Video-to-motion** — the creator performs the move on camera (the Creator's **Record motion** button, or `bitmagic generate animation --video <file>`). Uthana extracts the motion; the row is `source: 'generated'`, `origin: 'video'`, `prompt: 'video-to-motion'`, with `duration` set. Not an agent tool — you cannot record a video — but treat the result as any other custom clip.

- **Prompt-to-motion** — `bitmagic generate animation --video-prompt "a person waving both arms overhead"`. The same Uthana lane, but the source clip is *generated* rather than filmed: the CLI runs `generate video` first, appending capture framing (one person, whole body, static camera, no cuts) so the footage is something a pose estimator can read, then feeds that clip to video-to-motion. `--video-duration` sets the clip length (2-10 s, default 5). Two asset rows land: the clip as `type: 'video'` and the motion as `type: 'animation'` whose `sourceVideoUrl` is the clip. Billed twice, per second for the clip plus flat for the motion. Not an agent tool. At a terminal the command stops after the clip, writes 8 frames to `.bitmagic/videos/<assetId>.png` and asks before spending on the capture leg — `--yes` skips the question, and a run with no terminal (an agent, CI) never asks. If you decline, or if the motion leg fails, the clip is kept and the retry is `--video <that url>`, which costs nothing extra.

**Pinning a clip to a locomotion state without code:** any animation asset may carry `locomotionState: 'idle' | 'walk' | 'run'`. `loadAllAnimationAssets` reads it and calls `setAnimationOverride` for the player and every NPC that loads the pack (last asset wins per state). Write it through `edit-world-config` (an `upsertRoot` on `assets` keyed by `id`) — the data-driven form of `@docs locomotion-assignment.md`.

**Both target the canonical Mixamo skeleton** — every clip comes back with `mixamorig:*` joint names matching the engine-shipped `New*` clips' rig. Client-side, `CustomAnimationSystem.loadCustomAnimation` routes both `'uploaded'` and `'generated'` clips through `MixamoAnimationPlayer` (the same path the built-in Mixamo clips use), so they blend cleanly with locomotion and one-shots via world-transform reads. No retargeting needed.

Before playing, load once:

```typescript
await playerController.animationController?.loadCustomAnimation?.('mUserUploaded01');
playerController.animationController?.playCustomAnimation?.('mUserUploaded01');
```

Or load every animation asset at startup:
```typescript
await playerController.animationController?.loadAllAnimationAssets?.();
```

After loading, `playCustomAnimation` works exactly like for built-in animations. Same options (`speed`, `splitBodyOnRun`, `filterRootMotion`, `interruptOnMovement`, fade durations, `onFinished`, `onImpact`, `impactTime`) apply.

**Skeleton compatibility:** uploaded/generated humanoid clips must target the canonical Mixamo skeleton. `MixamoAnimationPlayer` rejection is an error, not an automatic standard-mixer retargeting fallback. Retarget incompatible source rigs offline before registration; see `game/docs/character-animation.md`.

## Authoring specs (generate-animation)

`generate-animation` builds a clip from a parameter spec — the only route
(no text-to-motion service). Free, deterministic, ~1s, bind-pose-correct by
construction, validated and gated by the same checks as the built-in library
(loop seam, grounding, root motion). A rejected spec names the failing field:
fix it and retry.

| family | covers |
|---|---|
| `gait` | walk/run variations — speed, weight, lean, arm drive, limps via `limpSide`/`limpDepth`, HELD arm poses via `dials.arms` (zombie reach ~`pitch: 1.43`, sleepwalker, low carry `< 0.85`; the 0.85–1.3 band lands hands at waist height and the build rejects it for a reach) |
| `melee` | weapon strikes as key poses — grip, blade direction, impact phase |
| `oneShot` | waves, salutes, bows, crouches, celebrations, flinches |

**Two different ids, don't conflate them.** `spec.motionId` is the clip's own
engine id baked into the GLB and must match the built-in convention — `m` plus
4+ letters/digits (`mBoatSeatedHold01`), same as `mWalkDefault01`. The minted
`asset_…` id from the manifest goes in the tool's separate `assetId` argument;
that is the id written to `world.json` and the one `playCustomAnimation`
resolves. Putting the asset id in `spec.motionId` is rejected.

**Root motion is handled for you.** A `gait` clip bakes real hips travel
(`designSpeed` × duration), exactly like the built-in locomotion clips. It
will NOT move the character — the engine locks a custom animation's root
motion at play time; position stays with the movement controller (opt in with
`applyRootMotion` to commit the step). Pick `designSpeed` for how fast the
motion should *look*.

**Stride sync (no foot sliding).** A clip installed as a locomotion state
(`setAnimationOverride(AnimationState.WALK/RUN, motionId)`) is speed-matched
to the character's actual movement, up to 3x. Native speed comes from baked
root motion, with the asset's `designSpeed` as fallback — authored `gait`
clips write both automatically. Beyond 3x the clip and the character's
`moveSpeed` genuinely disagree: lower `moveSpeed`/`chaseSpeed` or author a
faster gait. Legacy in-place generated clips (no root motion, no
`designSpeed`) play at 1x and slide at any speed — set `designSpeed` on the
world.json animation asset or regenerate as an authored `gait`.

**Strikes**: shape keys as guard → wind-up → contact → follow-through →
guard, with asymmetric easing — `ease: 'out'` settling into the wind-up,
`ease: 'in'` through the strike. Symmetric easing reads mushy even when the
geometry is right.

## Important notes

- **Don't trigger an animation every frame** — `playCustomAnimation` restarts the clip each call. Guard with `isPlayingCustom()` if you'll call it from a `keydown` handler that auto-repeats, or from update-loop code.
- **`filterRootMotion: true` for in-place moves** (most cases): flips, dodges, punches, idle gestures. Locks the hips position track so the clip rotates in place and physics owns translation.
- **Root motion is locked by default.** `filterRootMotion: false` opts into the clip's visual hips travel without moving the physics body. For gameplay displacement, use `applyRootMotion` with `onRootMotionDisplacement` and let the movement/physics system apply it.
- **`loop`** explicitly selects repeating or one-shot playback. `loadCustomAnimation(id, { loop })` stores a playback default; `playCustomAnimation(id, { loop })` overrides it for that play. Stop repeating custom clips with `stopCustomAnimation()`.
- **`splitBodyOnRun: true` for upper-body actions** (punches, gestures, throws, casts). Has no effect when standing still — the full body plays the animation as normal — but during a run the legs keep cycling instead of snapping to the clip's pose.
- **`interruptOnMovement: true` for one-shot moves that should yield to control** (kicks, dodges). The clip is cancelled the moment the player has movement input and locomotion resumes. Don't combine with long emotes/gestures the player should not be able to walk out of.
- **`speed`** scales playback. Default 1.0; punches/kicks feel sluggish at 1.0 — use **1.5** for snappy combat-style impacts. Doubling (`2`) is for very snappy/twitchy moves; halving (`0.5`) is for weighty / slow-mo. The forward flip auto-plays at `2` (see `PlayerController.onJumpTriggered`).
- **Fade durations** affect blending in/out. Short (0.1–0.2s) feels responsive; long (0.4–0.6s) feels smoother. Choose by feel.
- **The animation plays on track B** while the locomotion track A continues underneath. The renderer blends them via `MixamoAnimationPlayer.getBlendWeight()` which ramps over the configured fade durations — no manual blending needed.

## Runtime speed scaling & root motion

- `MixamoAnimationPlayer.setSpeed(s)` / `getSpeed()` — `0` freezes on the current frame, `1` is authored speed. Callers clamp to `[0.1, 2.0]` for locomotion.
- Locomotion speed matching: `setSpeed(moveSpeed / player.getNativeLocomotionSpeed())`, clamped. The native speed is measured ONCE at clip load from the hips XZ root motion (scaled to the character's height), after which the XZ track is locked to frame 0 so authored motion never fights code-driven movement. Re-calling the measurement returns the preserved value.
- Clips without root motion (in-place) fall back to `designSpeed` (set via `setDesignSpeed()` or the animation asset entry).
- RUN-state Mixamo overrides register first-wins — load the slower-designed clip first so moderate speeds scale sensibly.

## Debug: cycle through every animation when the user asks to test them

When the user asks to **step through / test / verify every animation**, wire `AnimationTestCycler` into the template's `Game.ts` setup. The default cycle list is `ALL_BUILTIN_MOTION_IDS` — EVERY clip the active library ships, on-demand packs included: locomotion, strafes/backpedals, postures (crouch, crawl, sit, kneel, swim, climb, cover, ledge, carry, push, ride) and their one-shots, weapon holds and strikes. The user presses **N** for next, **B** for previous; each clip loops until they advance.

Any of those ids also plays on its own — `playCustomAnimation('mGenCrawl01')` lazy-loads a pack clip by id the same way `mSoccerKick01` does, so "show me the crawl" needs no posture and no pack wiring.

```ts
import { AnimationTestCycler, DEFAULT_ANIMATION_TEST_CYCLER_OPTIONS } from 'debug/AnimationTestCycler.js';

// After playerController is constructed (in Game.ts, after the engine has wired it up):
const cycler = new AnimationTestCycler(this.playerController, { ...DEFAULT_ANIMATION_TEST_CYCLER_OPTIONS });
cycler.enable();
```

Test a custom list (e.g. just a Uthana dance + a freshly generated motion):

```ts
const cycler = new AnimationTestCycler(this.playerController, {
    ...DEFAULT_ANIMATION_TEST_CYCLER_OPTIONS,
    motionIds: ['mDanceUthana01', 'mYourGeneratedMotionId'],
});
cycler.enable();
```

**Notes:**
- Lives in `src/debug/`, so it's importable from templates and genre code but **not** from `src/engine/` (architectural boundary).
- Hooks `window.keydown`. Override `advanceKey` / `previousKey` (e.g. `'KeyP'`/`'KeyO'`) if the template already uses N/B.
- Remove the lines (or call `cycler.disable()`) when the user is done testing — leaving it active in shipped code would intercept N/B forever.

## When to use which

- **Unarmed combat (punch + kick fighter)?** `playerController.setAttackSystem(new UnarmedMeleeSystem(engine, physicsWorld))` — the system auto-registers `mPunching01` and `mKicking01` as `punch`/`kick` moves with correct hand/foot bone routing. No pack load required. See `combat-system.md` → "Player Unarmed Combat" for tuning.
- Want a one-off button-mash effect (no combat system, no hit detection)? Just `playCustomAnimation('mPunching01', { speed: 1.5, splitBodyOnRun: true })` per click.
- Sports / ball game (kick a ball)? **Use `BallSportsSystem`** (`engine/BallSportsSystem.js`) — it plays `mSoccerKick01` with contact-frame impulse + foot-contact gating. See `mechanic-soccer.md`.
- Mining / pickaxe / chopping action? **Use `PlayerToolSystem`** (see `voxel-mining.md`) — it attaches the pickaxe to the right hand and plays `mMiningChop01` for every swing. For a one-off chop without the mining sweep, `playCustomAnimation('mMiningChop01', { speed: 2.5, filterRootMotion: true })` is the same swing the tool system uses.
- Special movement / parkour? `mForwardFlip01` for any flip moment (the engine auto-plays it on double-jump; you can also trigger it manually for cutscenes / events).
- **Anything else?** Either have the user upload a GLB through the asset pipeline, or author one with the `generate-animation` tool (spec families: gait / melee / oneShot — no text-to-motion service). Both paths target the canonical Mixamo skeleton and play via the Mixamo player path.
