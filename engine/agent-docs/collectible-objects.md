# Collectible & Interactable Objects

Patterns for making environment objects interactive. Choose based on the interaction type and on WHERE placement positions come from.

## When to Use Which Pattern

| Pattern | Use For | Interaction | Example |
|---------|---------|-------------|---------|
| **A: Proximity auto-collect (CLI-placed)** | Items at FIXED positions known at authoring time | Automatic via Rapier trigger sensor | Coins, gems, mushrooms, power-ups |
| **A2: Proximity auto-collect (code-spawned)** | Items at positions COMPUTED by game code (procedural levels, drops) | Same sensor, spawned via `engine.spawnAsset()` | Coins along generated platforms, loot drops |
| **B: E-key interactable** | Objects the player deliberately activates | Press E / tap button | Doors, switches, chests, NPCs, cannons |
| **C: Carry and place** | Objects the player picks up, carries, and deposits | E to pick up, E to drop/place | Chickens, crates, keys, rescued NPCs |

In every pattern the asset itself is an entry in world.json `assets[]` (generated by asset tools, referenced by id or name). Patterns A/B resolve it by `--asset NAME` through the CLI; Pattern A2 resolves it in code by id or name.

## Pattern A: Proximity Auto-Collect

Place with the voxel CLI using `--collectible` (plus `--place-on-terrain` and `--name` for identification; use `batch-place` for 3+ — see `voxel-cli`):

`exec node bin/voxel.mjs place --asset mushroom --x 10 --z 15 --collectible --place-on-terrain --name mushroom`

The engine then does everything: a Rapier trigger sensor (2.0-unit radius) per collectible, auto-fire on player entry, hide + physics removal, one-shot sensor disposal. Game code only listens: `getInteractionManager().onCollected((objectId, objectName, object3D) => …)` from `engine/InteractionManager.js` — branch on `objectName` (the `--name` value) to update counters/HUD. No distance checks, no update-loop polling.

Collection works on foot **and from the driver's seat**: entering a vehicle removes the player capsule from the simulation, so the engine attaches a chassis-sized pickup probe to the vehicle for as long as a player is driving it (`engine/DriverPickupProbe.js`) — driving over a collectible collects it, no game code. Driverless / AI-driven vehicles have no probe and collect nothing.

## Pattern A2: Code-Spawned Collectibles (`engine.spawnAsset`)

When positions are computed at runtime (coins along a procedurally generated level, drops, respawning pickups), spawn the asset from game code instead of the CLI:

```typescript
const coin = await this.engine.spawnAsset?.('golden_coin', {   // asset id or name from world.json assets[]
    position: { x, y, z },
    collectible: { radius: 1.5, onCollect: () => this.addCoin() },
});
// coin.object (THREE.Object3D), coin.objectId, coin.dispose()
```

One call handles asset resolution (id/name → URL), fetch (once per asset — instances clone), VXL metadata (atlas mode, voxel size), scene + ObjectIdService registration, the collect sensor, hide-on-collect, and InteractionManager wiring — global `onCollected` listeners fire for these too. Other options: `rotation`, `scale`, `name`, `collision: true` (static collider, VXL only), `parent`. Returns `null` (with a console warning) if the asset doesn't exist yet or isn't spawnable.

Keep the returned handles and call `dispose()` when a pickup or arena is finished; repeated calls are safe. GLB spawns own independent geometry and materials, including material arrays, so editing a material's colour or collecting one instance cannot invalidate another. Textures remain shared: do not mutate or dispose them per pickup. Replacing geometry, materials or textures with resources allocated by your game makes those replacements your responsibility; the handle still releases its original resources. Prefer editing the provided materials in place for per-instance colours.

The engine releases all remaining handles and cached templates on game reload or engine disposal. A load that finishes after that teardown releases its resources and returns `null`. Arena travel within the same game still needs a generation check around each asynchronous spawn: if travel occurred while awaiting it, dispose the returned handle immediately instead of adding it to the new arena. Disposing arena handles leaves the template cache warm for the next visit.

**Do NOT hand-roll this.** There is no `VoxelObject.loadFromUrl` / `loadFromAssetId` — and manually doing `fetch(asset.url)` + `new VoxelObject()` + `loadFromFile(buffer)` + `CollectibleComponent` re-implements engine internals (metadata parsing, physics, registration) that `spawnAsset` already owns. If you find yourself searching the engine for how to load a VXL asset from code, the answer is `engine.spawnAsset`.

## Pattern B: E-Key Interactable

Place with `--interactable` (creates an individual VoxelObject instead of batching into InstancedMesh, so the interaction system can target it):

`exec node bin/voxel.mjs place --asset treasure_chest --x 30 --z 40 --interactable --name chest`

Then implement the `Interactable` interface (`types/interactable.js`) and attach an `InteractableComponent` (`engine/InteractableComponent.js`, needs `physicsWorld` + `{ interactable, object3D, radius }`). Key methods: `onInteractStart(): boolean` (the action), `getInteractStartDisplayName()` (the "[E] …" prompt text), `interactionEnabled()` (prompt visibility), `dispose()`. Find placed objects via `VoxelObjectBuilder.getObjectsGroupedByName()`.

Reference implementation: `samples/interactable-chest.ts` (a one-shot chest + wiring for every placed `chest`).

## Pattern C: Carry and Place

Two engine components (`engine/CarryableComponent.js`, `engine/DropZoneComponent.js`):

- **CarryableComponent** — E-key pickup; while carried the object follows the player, physics disabled. Simple objects (crates, keys) get their own sensor via the constructor; animals/NPCs use `CarryableComponent.fromAnimal(animal, physicsWorld, config)`, which wraps the entity's EXISTING behavior with carry interaction — never build a custom behavior class for carrying.
- **DropZoneComponent** — a named target area (`{ position, radius, name, displayName, onObjectPlaced }`). Carrying near a zone flips the prompt to "[E] place X in Y"; placing re-enables physics and fires `onObjectPlaced`. Pressing E outside any zone drops in place.

Global events: `onCarryEvent(listener)` / `removeCarryEventListener(listener)` — events `'pickedUp' | 'dropped' | 'placedInZone'` with object name and zone.

Reference implementation: `samples/carry-and-drop.ts` (crate storage + carryable chicken + global events).

### CarryableComponent API

| Method | Description |
|--------|-------------|
| `CarryableComponent.fromAnimal(animal, physics, config)` | Static: wrap an AnimalController for carrying |
| `state` | Current state: `'idle'`, `'carried'`, or `'placed'` |
| `isCarried()` | Check if currently being carried |
| `onInteractStart()` | Toggle pickup/drop (call from behavior's `onPlayerInteract`) |
| `getInteractStartDisplayName()` | Get current prompt text (call from behavior's `getInteractDisplayName`) |
| `forceDrop()` | Force-drop the object (e.g., on player death) |
| `dispose()` | Clean up physics sensor |

### DropZoneComponent API

| Method | Description |
|--------|-------------|
| `canAccept()` | Check if zone has capacity for more objects |
| `getPosition()` | Get zone center position |
| `getPlacedCount()` | Number of objects placed so far |
| `DropZoneComponent.findZoneAtPosition(pos)` | Static: find zone at world position |
| `DropZoneComponent.findZoneByName(name)` | Static: find zone by name |
| `dispose()` | Clean up physics sensor and unregister |

## Common Mistakes

1. **Scene traversal for batched objects** — Standard placed objects (without `--collectible` or `--interactable`) are batched into InstancedMesh. You cannot find them by traversing the scene. Use `--collectible` or `--interactable` to get individual Object3Ds.

2. **Manual distance checking for collectibles** — Don't write `update()` loops with distance checks. Use `--collectible` which uses efficient Rapier trigger sensors that fire automatically.

2b. **Hand-rolling runtime asset loading** — Don't `fetch()` an asset URL and feed it to `new VoxelObject().loadFromFile()` yourself, and don't search the engine for `loadFromUrl` (it doesn't exist). `engine.spawnAsset('name-or-id', { position, collectible })` is the supported path for code-computed placements (Pattern A2).

3. **Forgetting `--place-on-terrain`** — Without this, objects use the Y from physics raycasting at placement time. With `--place-on-terrain`, the EnvironmentObjectSystem adjusts Y to terrain height at load time, which is more reliable for procedural terrain.

4. **Creating new keyboard bindings** — Never add custom key listeners. Use the Interactable interface (Pattern B) for E-key interactions, or `--collectible` for auto-collect (Pattern A).

5. **Using both `--collectible` and `--interactable`** — Pick one. `--collectible` auto-collects on proximity. `--interactable` waits for E-key press. They are mutually exclusive.

6. **Building carry logic from scratch** — Don't write custom pickup/attach/drop code. `CarryableComponent` + `DropZoneComponent` handle E-key toggling, player attachment, drop-zone detection, and events.

7. **Calling `carryable.update()` manually** — The engine updates all CarryableComponents each frame via PlayerController. No manual update loop needed.

8. **Disposal** — Every interactable/carryable/zone created in setup must be disposed in the game's `dispose()` (see the samples).
